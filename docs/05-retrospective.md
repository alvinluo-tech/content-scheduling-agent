# 05 · 复盘

## 最难的三件事

1. **让"决策依据"成为一等公民。**
   最初工具没有 `reason` 参数，trace 里只有"调用了什么"，说不清"为什么"。改成每个工具强制 `reason` 后，
   模型每一次选择都被迫给出一句话依据，评审能直接看出它是不是真的在看上一步结果。
   这也暴露了一个真问题：查时段没有 `material_id` 时，连"这一步属于哪条素材"都判断不了——归因缺失会直接让循环失控。

2. **硬性要求与"能排上"之间的张力。**
   业务上既要尊重用户"必须 18:00"，又要在冲突时给出可用方案。把它做成状态机而不是文案：
   改期必须有一条 pending 的确认记录，草稿才能落库，且草稿状态是 `draft_pending_confirmation` 而不是 `draft_ready`。
   关键判断是——**宁可交出"待确认"，也不要交出一份看起来完成的排期**。

3. **重复提交的语义。**
   "同一请求重复保存只产生一份草稿"听起来简单，但草稿也占位：如果不排除素材自己的草稿，
   重提时原时段会变成"被占用"，草稿被悄悄挪到别的时段——表面去重了，实际改了排期。
   最后统一口径：去重键 `date|material_id|requested_time`，占位计算一律排除自身。

## 学到什么
- 护栏要写在**代码和数据结构**里（没有发布工具 = 不可能发布），提示词只是提醒。
- 报告字段要从工具账本反查，不能采信模型自述；"模型说保存成功"不是证据。
- 一个状态字段承载不了两件事：`completed` 与 `outcome` 分开之后，保存失败的语义才不再自相矛盾。
- 离线 Mock 的价值是**可回归**，不是"证明模型行"；两者必须分开陈述，否则评估文档本身在虚报。

## 实际用时
约 3 小时（需求拆解与验收点设计 30 min、工具与图实现 70 min、测试与用例 40 min、文档与归档 40 min）。
另加约 40 min 的 Web 演示层：`src/server.py`（标准库 HTTP）+ `web/` 三文件（无构建步骤）+ 11 个接口测试。
界面迭代里返工最多的是时段带（格内塞文字互相溢出 → 改成密度色块 + 刻度行 + 明细列表），
这说明"把报告照抄到屏幕上"并不等于可读——同一条 `report` 需要一层为阅读服务的排版。
之后又花了一轮在界面上做**实时推送**：起初界面是「点一下、转圈、一次性出结果」，真实模型要跑十几秒，
过程全空着，等于把 Agent 最有信息量的部分藏起来了。改成 `TraceRecorder` 观察者 + SSE 之后，决策一条条长出来，
顺带暴露了一个语义问题：上一轮的结论在新一轮跑完前还亮着，容易被当成当前结果——现在会先压暗。
再一轮花在**多日排期**上：题面只要求「发布时间要求」，但原实现把一天当成了全部世界，跨天请求无处可去。
扩多日时踩到的坑是去重键——一度想改成按建议结果（`scheduled_time`）生成 `draft_id`，
结果 02 的 id 会随改期漂移、与账本里已有的 `scheduled_time` 脱节；最终回到「去重键跟用户要求走，改期只体现在 `scheduled_time`」。
同时把硬性护栏从「时间变了」推广成「时间或日期变了」，否则跨日就等于绕过确认。
还有一次不算功能、但必须记的返工：拿真实模型跑多日用例时，模型在结论里指出
「11-13 09:00 的占用方显示为 M07，而 M07 本次申请的是 20:00，两者矛盾」——查下去确实是我造的
`schedule.json` 把 M07/M06 既写成已有排期、又让它们在同一用例里申请新时段。合成数据也会自相矛盾，
现在 11-13 的已有排期换成 M02/M00，与 07 用例的素材不重叠。这条是"真实模型跑一遍"抓出来的，
离线 Mock 只会照着数据算冲突，不会质询数据本身。

最近一轮把「建议时段」从"第一个空闲格子"改成**可解释的排序**：距离、与已有排期的间隔、偏好档三项，
每条理由都随工具结果返回，所以报告里的建议不是模型编的，也不是我拍脑袋定的。
写这一轮时发现一个典型陷阱：把 `min_gap_minutes` 默认设成 60，会把 07 用例的 09:30 顶到 10:00，
而 09:30 本身完全合法——偏好配置一旦写大就会悄悄改变"最近可用"的语义。最后数据里取 30（一格），
用一个显式传 60 的测试证明惩罚真的会生效，避免"配置存在但永不触发"。

界面这一轮补的是"用起来顺不顺手"：顶栏显示本轮真实耗时（不是写死的估算）、
场景列表可以用方向键走、焦点有可见描边、读屏能从 `aria-live` 听到结论变化，
并把 884px 窄屏的样子截了图——之前所有截图都是宽屏，等于从没验证过窄屏。
一条经验：截图前要确认服务进程是最新的——这次 07 的场景说明还停在旧文案，
截图里写着"M07 占用"，而数据早改成 M02；改完源码不重启就拍照，等于给自己留假证据。

这一轮补的是**当天排满**这个空档：原来的替代时段只在同一天里找，一天排满就等于"没有建议"，
而真实排期里"今天满了改明天"是最常见的一次决策。实现上刻意不新开一行代码路径——工具只是多返回一个
`next_available`，改期仍然要过 `time_hard` 的确认护栏，所以 08 的草稿停在待确认，而不是被模型自作主张推到第二天。
顺带给界面补了两处：素材行现在同时写出"要求 2026-11-14 18:00 / 建议 2026-11-15 09:30 / 已改日期"，
跨日默认选中的是用户要求的那一天（先看"在跟哪一天较劲"），改期结果写在素材行里。

补掉的是**确认之后的另一半**：原来只有"同意"这一条回写通道，人不同意时无处表达，
模型下一轮还能把同一个替代方案再存一遍。现在否决会同时做三件事——确认项标 `rejected`、
那份待确认草稿标 `draft_rejected`、`save_draft` 对同一替代时段返回 `CONFIRMATION_REJECTED`。
第三条最关键：否决不是提示词层面的"请勿打扰"，而是账本里一条谁都绕不过去的记录；
离线 Mock 收到它直接收尾，报告写"改期被否决"，而不是把失败说成部分成功。

这一轮补的是"频道"这一维。原来占位键只有日期，同一时刻只说得出"被谁占"，说不出"被谁在哪个频道占"——
短视频频道和主频道在同一分钟各有一条排期，本是两件不同的事。改法是把频道放进三处身份：占位读取、草稿去重键、
确认项键，并在 id 上显式带后缀（`D-M02-2026-11-12-1200-shorts`），这样"不串道"由数据形状保证，
而不是靠模型记得切频道。给出的教训是：给已有函数补一个维度时，最容易漏的是**键**（去重、幂等、确认项），
而不是分支；漏了键之后表面上功能正常，只有"同一素材在两个频道各排一份"这种用例才暴露。

补的是"人不同意模型给的那个时段"的第三条路。原来只有同意 / 不同意两个按钮，人要是想排到 20:30
而不是 19:00，只能先否决再口头说明——模型并不知道人挑的是哪个时段。现在 /api/reject 带上 time 就是"否决这一版、
把人挑的时段记为已同意"（`replanned_from` 指回原方案），重跑时模型先撞 CONFIRMATION_REJECTED、
再按候选往下找，最终落在人挑的那个时段。顺带把工具查过的候选（`slot_options`）写进报告，
界面才能给人一个下拉框，而不是让人自己敲时间。

这一轮补的是"两个进程同时写同一份账本"。原子替换只能保证文件不会被写坏，挡不住丢更新：Web 演示层和 CLI
各持一份内存快照，谁先读完谁后写，后写的那次就把前一次的数据整份覆盖掉——本地演示时几乎撞不到，但它属于
"看起来成功、实际丢了一条草稿"的那类问题。改法是把三件事绑成一个事务：拿锁（跨进程）、重读磁盘、再改再写；
`save_draft` 更进一步，把"查冲突"也放进同一把锁里，否则两个并发运行会都看到空位、各写一份。锁等不到就报
`LEDGER_BUSY`，宁可让这次运行失败，也不要把不确定的结果当成功。给出的教训是：凡是"读-改-写"的存储，
原子写 ≠ 并发安全；而并发 bug 的测试必须能被证明有牙——我用"把事务换回空壳"跑了一遍，草稿数从 2 掉到 1。
