# 04 · AI 辅助使用说明

> 题面要求：如实记录**使用范围、个人贡献与验证结果**。下面三节分别对应这三项，不给体面的措辞，只给能核对的事实。

## 一、使用范围（AI 用在了哪些环节）

AI 编码助手（DeepSeek Harness 内的 Agent，模型 DeepSeek）承担了这个仓库绝大部分的**敲键量**：初稿代码、测试、文档、界面。人承担的是决策与验收（见第二节）。

| 环节 | 由 AI 产出 | 人做了什么 |
| --- | --- | --- |
| 项目骨架与模块划分 | `src/` 下 10 个模块的初稿、依赖与目录结构 | 定「CLI 主入口 + 可选 Web 薄壳」的形态，否掉 HTTP / Notebook |
| 工具实现与护栏 | 5 个工具的 schema、参数校验、五道守卫、去重键 | 定三条红线（不发布 / 改硬性时间需确认 / 审核不过不写草稿）必须由代码强制 |
| 推理链路 | `src/graph.py` 的 StateGraph、条件边、步数上限判定 | 否掉 `create_react_agent` 一行式，理由是步数上限与决策归因必须可插入、可断言 |
| 离线 Mock | `ScriptedChatModel` 的逐素材状态机 | 定「保存失败只重试 1 次后如实放弃」「否决后不得再存同一方案」等退出条件 |
| 报告与渲染 | `report.py` 的字段反查、`markdown.py` 的排版 | 定「报告只从工具账本反查、模型自述单独成段并标注不作证据」；`completed` 与 `outcome` 拆成两维 |
| 测试 | 105 个 unittest 的初稿 | 挑验收点、要求关键守卫必须有反例测试（故意越权保存、故意重复提交、故意让存储失败、故意篡改报告） |
| Web 演示层 | `src/server.py` + `web/` 三件套（SSE、口令、自定义请求、账本面板） | 定「界面不是第二条链路，必须复用 `run_pipeline()`」；每轮亲眼看截图 |
| 合成数据 | M00–M07 素材、规则、4 天 × 2 频道的占位 | 设计冲突布局：让 19:00 成为 18:00 之后第一个可用时段，从而逐字复刻题面参考实例 |
| 文档与 README | 5 篇 docs 与 README 的初稿 | 逐条核对事实（测试数、用例数、字段名），把写错的数字与失效的说明改掉 |

**没有使用 AI 的部分**：没有用 AI 生成任何密钥、真实素材、真实用户数据或第三方版权素材；`data/` 全部为合成数据，`.env` 未入库，仓库里没有一个真实 `DEEPSEEK_API_KEY`。

## 二、个人贡献（人负责的部分）

1. **题面拆解与验收点映射**：把「必须验收」的 6 个场景翻译成可执行用例与断言，先定验收再看代码；后来扩展到 10 个用例（多日、顺延、多频道、同轮竞争）。
2. **方案取舍**：否掉一行式 ReAct，选显式 StateGraph；把「请求确认」做成第 5 个工具而不是提示词，理由是确认动作要有参数、有返回、能在 trace 里被看见。
3. **红线设计**：不发布（工具集里没有发布能力）、硬性时间或日期被改动必须先有确认项、审核未过不许排——三条都要求代码强制而非提示词约束。
4. **报告可信度设计**：字段全部从工具账本反查；`completed` / `outcome` 两维；每条素材带「下一步」；没有证据的结论不进报告。
5. **人的四种决定**：同意 / 否决 / 改选 / 撤回都落成账本记录（`decided_by` / `decided_at` / `replanned_from`），否决会真正挡住同一方案，撤回只释放占位。
6. **数据设计**：占位布局刻意复刻题面参考实例；后来发现 11-13 让「正在申请新时段的素材」同时又占了旧时段，自相矛盾，改为 M02 / M00 占位。
7. **每轮验收**：跑测试、逐条读 trace、看界面截图、核对报告字段，不采信「跑通了」的自述。
8. **迭代方向选择**：每一轮补什么由人定（多日 → 顺延 → 多频道 → 并发锁 → 输入校验 → 人工四通道 → 口令 → 自查脚本），AI 负责实现与自测。

## 三、AI 产出中被我改掉的问题（真实记录）

| 问题 | 表现 | 修法 |
| --- | --- | --- |
| 查时段调用无法归因到素材 | `query_time_slot` 没有 `material_id`，离线策略按 `args.material_id` 归因失败，反复查同一时段直到撞上 20 步上限 | 工具增加必填 `material_id` 并校验素材存在，报告的 `touched` 判定同时修好 |
| 保存失败会无限重试 | 模型对 `SAVE_FAILED` 无退出条件，跑到步数上限才停 | 明确「重试 1 次后放弃并如实报告失败」 |
| 重复提交会把草稿改到别的时段 | `query_time_slot` 把素材自己的草稿也算占位，重提时 19:00 变「已占用」，草稿被挪到 19:30 | 占位计算排除自身素材，与 `save_draft` 口径一致 |
| `save_attempts` 语义重名 | 草稿里的「提交次数」与报告的「失败次数」同名 | 拆成 `submit_count` 与 `failed_save_attempts` |
| 「completed」会被误读成成功 | 保存失败时 `completed=false`，而流程其实正常结束了 | 拆成 `completed`（推理是否收尾）与 `outcome`（scheduled / pending_confirmation / partial / failed / incomplete） |
| trace 步号口径打架 | 并行调用时报告说 4 步、trace 有 5 条记录 | trace 用模型轮次而不是工具序号，同轮多个调用共享步号 |
| 频道标签点不动 | `replace_all` 把 `activeChannel = null` 也写进了点击处理器，点完立刻被清空，且不报错 | 读源码发现重复行；此后改多行文本先 `grep` 定位 |
| 有测试从未被执行 | `if __name__ == "__main__"` 被追加在文件中间，其后的用例缩进进该块，套件一直显示全绿 | 主守卫移到文件末尾，测试数 83 → 85；教训是「以断言真的执行过为准，不以测试数为准」 |
| 导出的报告缺输入文件 | `remember_report` 用 `run_id` 反查场景，而 `run_id` 被输入文件覆盖，永远匹配不上 | 改用调用方已知的 `case` |
| 自查脚本被上游用例污染 | 全部用例共用一份临时账本，06-step-limit 的 M02 被前面用例的草稿污染成 scheduled | 每个用例一份账本，只有 05-dedup 复用 02 的账本（去重证据） |
| README 行内代码整篇坏掉 | 批量写入时占位符收尾写错，全文每个行内代码都缺收尾反引号 | 两步正则修复后 `grep` 残留，确认清零 |

复现三条命令：

```bash
.venv/Scripts/python.exe -m unittest discover -s tests -t .   # Ran 105 tests ... OK
.venv/Scripts/python.exe scripts/run_examples.py              # 10 个用例，结论与归档一致
.venv/Scripts/python.exe scripts/verify_submission.py         # 12/12 通过
```

边界：Mock 证明的是流程与护栏，真实模型证明的是「模型在同样的护栏下也走对了」，两者都不证明生产可用（单文件账本、共享口令、静态规则、合成数据）。生产化需要改什么，见 `docs/03` 的「失败与限制」。
