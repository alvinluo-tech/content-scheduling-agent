# 01 · 需求

## 用户
内容团队的排期运营：每天拿到一批待处理素材，需要在已有排期里给它们找到不冲突的发布时间，然后把排期草稿交给发布同学确认。

## 要解决的问题
1. 素材能不能发（信息是否齐全、是否命中审核规则）。
2. 发在什么时候（用户要求的时段有没有被占，有没有可行的替代时段）。
3. 硬性要求能不能动（用户明确说"必须 18:00"时，改时段必须由人拍板，Agent 不得自作主张）。
4. 结果能不能被相信（保存成功就是成功，失败就是失败，重复提交不能变成两份草稿）。

## 范围内（本次实现）
- 输入：素材 ID、发布时间要求（可硬性、可指定日期 `requested_date`）、本次要处理的素材列表——一个 JSON 文件。
- 工具：素材读取、规则检查、时段查询、请求确认、排期草稿保存（5 个，全部可被模型自由选择与重复调用）。
- 输出：每项素材的审核状态、风险原因、缺失字段、建议时段、待确认项、草稿状态与保存结果，加逐步骤 trace。
- 动态决策：模型基于上一步工具结果决定"补查 / 换时段 / 请求确认 / 阻断 / 保存 / 重试"。
- 安全边界：只写草稿账本，不接任何真实发布通道；步数上限触发时明确返回未完成。

## 范围外（明确不做）
- 不做多 Agent 协作、不做真实发布、不做数据库（草稿用 JSON 账本）。
- 界面与 HTTP 不是题面要求：CLI 是主入口，`src/server.py` + `web/` 只是复用了同一条 `run_pipeline()` 的可选演示薄壳。
- 不做真实内容审核（规则为合成规则，语义审核不在本次范围）。
- 不做排期全局最优化（不追求填满时段，只保证不冲突且尊重用户要求）。

## 成功标准
| 编号 | 标准 | 判定方式 |
| --- | --- | --- |
| S1 | 至少一条"模型选动作 → 执行工具 → 观察结果 → 调整下一步"的完整闭环 | trace 中每步都有 `rationale` 与 `next_action`，且存在因工具结果改变动作的分支（02 冲突 → 请求确认；04 失败 → 重试后放弃） |
| S2 | 两条以上执行路径的运行记录 | `examples/02-conflict.trace.json`（冲突改期）与 `examples/04-save-failure.trace.json`（保存失败） |
| S3 | 有步数与工具调用上限，且超限返回明确未完成 | 06 用例：`status=step_limit_reached`、`completed=false`、`unfinished_materials` 非空 |
| S4 | 覆盖 5 个必须验收点（正常 / 冲突 / 缺失 / 风险 / 重复 / 保存失败） | `examples/*.output.json` 与 `tests/` 断言 |
| S5 | 不得越权发布 | 工具集无发布能力，报告 `published` 恒 false（`test_no_publish_tool_exists`） |
